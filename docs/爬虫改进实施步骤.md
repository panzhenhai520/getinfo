## 阶段 1：检索质量收口（已完成，作为后续基线）

**目标**：让"库里有、AI 搜得到"成立；让入库闸门不可绕过。

**子任务与边界**
1. 封死绕过点：生产模块禁止 `INSERT INTO articles`，禁止直接调 `insert_article`。
2. 清洗/判废前置到唯一漏斗（正文清洗 → 框架页判废 → 入库 → 归属 → 分类/精炼入队）。
3. 归属必填：入库与去重 update 两条写路径都保证至少一条包归属（落在该包「其他」）。
4. 入口收敛：所有采集/接口路径走 `ingest_article(source_kind=...)`。

**实现方法**：`sqlite_database.insert_article` 为唯一收口；`intel_attribution.ensure_pack_attribution` 写兜底归属并复用真实分类器打分（否则过不了检索质量门）；`article_ingest.ingest_article` 做来源白名单与统一标记。

**测试方式**
- `tests/test_ingest_choke_point.py`（AST 守卫 + 来源白名单 + 双路径接线断言）。
- `_tmp_attr_verify.py`（4 例）、`_tmp_manual_e2e.py`（4 例）、`_tmp_ingest_kinds_verify.py`（14 个来源真库写入）、`_tmp_fallback_retrieval_verify.py`。
- 生产容器内真库验收 + `ArticleRetriever._rows` 抽检。

**验收标准（已达成）**：三机"无任何包归属的活跃文章 = 0"；兜底归属行带真实行业证据并通过检索质量门；回归对比零新增失败。

## 阶段 2：可解释性——【证据解析】+【词元影响力】（已完成）

**目标**：让用户看到"为什么召回这些证据、为什么这句话引这篇"。

**子任务与边界**
1. 答案分解：LLM 优先、规则兜底；只拆不答。
2. 归因：证据句级召回 → LLM 判定 support/refute/irrelevant；**只能使用本次 run 的证据**，不允许引入外部知识。
3. 落库与幂等：与 run 绑定，重复点击不重算。
4. 接口 + 前端按钮。
5. 词元影响力一期：遮挡法，复用同一套结构与前端。
6. **边界**：归因失败绝不影响问答本身；词元影响力必须标明 method（代理法不得冒充梯度）。

**实现方法**：`qa_attribution.py`（`QaAttributionService`）+ 4 张表 + 2 组接口；打分后端三档自动选择（本地 transformers → HTTP 对数概率 → 重叠代理）。

**测试方式**：`tests/test_qa_attribution.py`（14 例纯函数）；真 run 端到端（`_tmp_attribution_verify.py`）；真实浏览器点击（`_tmp_attribution_ui_verify.py`，新起 Flask 实例 + chromium）。

**验收标准（已达成）**：真 run 产出信息单元与归因链路，至少一个单元找到支持性证据句；浏览器里按钮真点真渲染（`units=4 links=6`、影响力值出现）；重复点击命中缓存。

## 阶段 3：采集质量——Scrapling 会话复用与正文清洗（已完成）

**目标**：降低兜底抓取失败率与耗时；正文更干净。

**子任务与边界**
1. 会话复用（**每线程一个**会话，因同步 API 线程绑定；不能用进程单例）。
2. 降级：会话创建失败/损坏 → 先释放会话 → 回退"每次新建"。
3. 正文来源：`markdown(main_content_only=True)` 优先，但臃肿超阈值退回纯文本。
4. **边界**：返回值契约不变；直连路径行为逐字不变；不引入新依赖。

**实现方法**：`threading.local` + 模块级锁 + `atexit` 关闭；`CRAWL_SCRAPLING_SESSION_ENABLED`、`CRAWL_SCRAPLING_MARKDOWN_MAX_RATIO` 两个开关。

**测试方式**：`tests/test_crawl_retry_scrapling.py`（26 例）；真实公网 5 站对比脚本；多线程隔离脚本；4 类降级场景脚本。

**验收标准（已达成）**：复用路径成功且正文非空、字数与旧路径一致；重复调用耗时显著下降；坏域名与会话损坏时能回退且会话不崩；开关=0 时完全回到旧行为；既有用例通过数不减。

## 阶段 4：时间维度补前置（✅ 已交付）

**目标**：让"时间"从"加权 + 日粒度"升级为"可硬约束"，这是时间参与检索、主张时效、事件时间轴共同的前置。

**为什么必须等前置**：`articles.published_at_utc` 全表为空（0/6105），仅 `publish_date`（日粒度、5.4% 无日期）可用；没有可信时间戳，"指定某月/某机构某日""主张在什么时间区间成立"都无法落地。

**⚠️ 本轮发现的关联问题**：本地 RAGFlow 增强检索已熔断（`qa_circuit_states` 里 `ragflow` 于 2026-10-06T07:39Z 连续 9 次失败后打开），导致 `level2_retrieval.enhanced=False`、送进草稿的证据从 27~28 条掉到 7 条。**做任何"答案质量/耗时"的前后对比前，必须先确认 RAGFlow 在线**，否则数字会被这个变量污染（本轮复测就踩到了：synthesis 中位数 50.6s→25.4s 主要是 RAGFlow 掉线造成，不能归因于代码修复）。

**本轮已做（2026-10-08）**
1. ✅ **入库就写对四个时间列**：`sqlite_database.insert_article` / `update_article` 两条写路径统一调用
   `publish_time.article_time_fields()`，写入 `published_at_utc` / `published_timezone` / `published_precision` /
   `published_time_source`。**并修掉一个真 bug**：原实现用 `strptime('%Y-%m-%d')` 解析，RSS/JSON-LD 给的
   带时分串（`2026-10-07T14:30:00+08:00`）解析失败 → 整条日期被丢成 None（RSS 源因此大面积丢日期）。
2. ✅ **时区显式声明、不猜**：新增 `config/source_timezones.json`（publishers → markets → 全局默认），
   实际使用的时区写进 `published_timezone`，任何一条都能反推回源站本地日期。
   与既有读取方约定保持一致：`precision ∈ {date,day,url}` 时 `published_at_utc` 前 10 位**仍是源站本地日期**
   （见 `financial_evidence._article_time_interval`），换算成 UTC 会整体错一天。
3. ✅ **回填工具**：`tools/backfill_published_at_utc.py`（只读审计 → `--apply` → 自动导出备份 → `--rollback`）。
   取值顺序：已有 `publish_date` → URL 日期 → 正文首尾日期 → `first_crawled`（仅 `--include-discovered`，
   标 `precision=discovered`，硬约束会排除它）。
   本地实测：685 篇活跃 → 回填后 **100% 覆盖**（676 条 date 精度 + 9 条 discovered）。
4. ✅ **检索硬约束 + 分级扩窗**：`qa_retrieval.apply_time_gate()`：先用问题窗口硬过滤，窗口内不足
   `QA_TIME_MIN_IN_WINDOW`（默认 1）条时按 `QA_TIME_EXPAND_LADDER`（默认 3 月→6 月→1 年）逐级放宽；
   时间未知的文章**不丢**（排在窗口内证据之后并计数）。`QA_TIME_HARD_FILTER=0` 完全回到旧的"只加权"行为。
5. ✅ **调整里的时间范围优先**：`plan.time_window_adjustment`（ISO 字符串，SSE 安全）在检索侧直接替换窗口。
6. ✅ 配套：`qa_retrieval` 的取数 SQL 补上三个时间列（原来根本没 select，硬约束只能退回 `publish_date`）。
7. ✅ **精度贯通到展示**（此前只贯通了入库与检索）：
   · 证据卡：`_article_evidence()` 新增 `published_at_utc / published_precision / published_timezone /
     published_time_note`，把精度说成人话（"仅到日（源站时区 Asia/Shanghai）"/"精确到时分"/
     "时间未知（按首次抓取标记）"）；
   · 时间轴接口 `/api/intel/timeline`：返回 `date_precision` 与 `time_note`，并把原先**写死的**
     `date_inferred=False` 改成由 `precision=discovered` 推导（只有抓取时间的必须标出来）；
   · 前端时间轴：日期旁新增精度徽标（深蓝皮肤同步配色）。
8. ✅ **精度体检工具** `tools/audit_published_time.py`：分布（精度/来源/时区）+ 自洽性断言
   （`published_at_utc` 前 10 位必须等于源站本地日期、不得早于 2000 年、时区必须可加载；
   "未来日期"直接复用入库闸门的 `article_identity._is_implausible_future_date`——**+90 天内的
   预告日期是合规的**，审计不再自己定更严的线把它误报成错误）
   + 可复现的 200 篇抽样明细（`--seed`）供人工眼过；发现错位/非法时间时退出码非 0。
   本地实测：685 篇活跃 100% 覆盖；0 错位、0 超过 90 天的未来日期、1 条合规预告日期。

**边界**：不做时区猜测（无时区信息时按源站 locales 显式配置，禁止默认 UTC+8 硬填）；抽取不确定时宁可留空并标 unknown。

**测试方式**：`tests/test_publish_time.py`（+7 例：日期字面量约定、时区声明、精度归一、不编造时间）、
`tests/test_qa_time_hard_filter.py`（15 + 6 例：本地日期归属、硬过滤、阶梯扩窗、开关回退、未知时间不丢、
精度文案与证据字段）、`tools/audit_published_time.py`（分布 + 自洽性 + 抽样）。

**验收标准（已达成）**：本地 685 篇活跃文章 `published_at_utc` 覆盖 **100%**（≥90%）；`published_precision`
分布可查（date 676 / discovered 9）；硬约束关闭时行为回到当前（单测钉死）；"最近一周"类问题不再返回超窗文章。
**说明**：原文要求的"200 篇抽样人工核对"改为**工具化核对 + 可复现抽样明细**——人工逐篇看不现实，
但"日期错位/非法时间/时区不可加载"这些**人眼能发现的问题已变成断言**，人工只需过一遍工具打印的样本表。

## 阶段 5：调整思路真正生效（✅ 已交付，方案 §5.2）

**目标**：让用户在规划阶段提的调整**改变检索与生成**，而不是只换模板。

**实测问题（已确认）**：调整确实到后端并进了 plan（`user_adjustment`、`answer_strategy`、`answer_template`），但 `subquestions` 与 `queries` 不变、送模证据不变 → "查看政策全文，逐段解释"只是"听话了但没做到"。

**本轮已做（2026-10-08）**
1. ✅ **调整意图扩字段**：`_normalize_adjustment_patch` 新增 `retrieval_queries` / `time_window` /
   `must_fetch_fulltext` / `output_form`（`paragraph_by_paragraph|structured_text|table|timeline|brief`），
   旧字段 `format` 自动映射到 `output_form`。
2. ✅ **调整落到检索条件**：专项检索式插在 `plan.queries` **最前**（保证在 `query_cap` 截断前保留）；
   规则路也认"全文/逐段/原文/表格/时间"这些说法（原先规则路只认 confirm/filter，其余全靠 LLM）。
3. ✅ **时间范围真生效**：`plan.time_window_adjustment`（ISO 串，SSE 安全）在 `qa_retrieval` 里**优先于**
   问题文本解析出的窗口；相对说法给区间、绝对说法（2026 年 1 月）给精确 start/end。
4. ✅ **全文通道**：`must_fetch_fulltext` 时证据正文上限从 5000 提到 `QA_FULLTEXT_EXCERPT_CHARS`（默认 12000），
   走库里采集时抓下的原文，不新增网络依赖、不绕过证据闸门。
5. ✅ **回执**：`adjustment_receipt`（"已按『逐段解释』组织回答；检索式已加入专项查询：…"）随 plan 阶段
   作为 `stage_progress` 消息推给用户，并写进合成阶段的计划摘要（`输出形式` / `原文全文逐段` / `调整回执`）。
6. ✅ **澄清闸门升级**：plan 卡片在「继续 / 调整思路」之外给出 3 个一键调整
   （逐段解释原文 / 只看最近 3 个月 / 用表格对比），点击走同一条 `pendingPlanAdjustment` 通路。
7. ✅ LLM 解析器 prompt 与 `required_json_shape` 同步扩字段（模型现在能直接产出这四项）。

**边界**：不得改变"用户没调整时"的行为路径（单测钉死：无调整时 output_form 为空、queries 不新增全文式）；
LLM 解析失败必须回落到规则/确认语义；专项检索式必须仍走既有召回与引用校验。

**测试方式**：`tests/test_qa_plan_adjustment.py`（新增 16 例：规则路识别、`plan.queries` 行为断言、
时间窗口、无调整回归、"同意/继续"不调 LLM、patch 归一化上限与非法值）。

## 阶段 6：一级检索模式的真实提速（P1，方案 §4.2 修正版）

**目标**：在**不牺牲引用召回**的前提下降低端到端时延。

**实测修正**：原"草稿通过就跳过 synthesis"不可行。真正的收益点（本轮已完成前两条）：
1. ✅ **`max_tokens` 截断修复**：本地模型输出上限 900 → 可配 `QA_LEVEL1_LOCAL_MAX_TOKENS`（默认 2400）。API 直测：900 → `finish_reason=length`、JSON 截断；2400 → `stop`、实际只需 1256 token（峰值 1341，余量 79%）。

## 阶段 7 验收口径修正（2026-10-09 定稿：① 改分母 + ③ 换真指标）

**为什么要改**：用户提问"覆盖率 60% 怎么处理"，实测发现这是**分母不合理**，不是抽取不行。
库里有大量天生没有事件的文章（政策解读/科普/行情/榜单/主系表属性句），把它们算进分母，
等于要求"所有新闻里 60% 都有明确事件"。A 机实测（6522 篇活跃）：

| 准入政策 | 可抽文章 | 旧口径天花板 |
|---|---|---|
| 当前口径（趋势/事件类 + 命中锚点） | 4634 | 46% |
| 放宽锚点要求 | 4635（+1） | 46% |
| 纳入 `other` 类 | 5535（+901） | 54% |
| 两者都放宽（极限） | 5805（+1171） | **57%（仍不到 60%）** |

结论：**锚点不是瓶颈（放宽只多 1 篇），旧口径的 60% 不可达**；把 `other` 类全抽进来也只到 57%，
还会把"不是事件的东西"灌进图里污染检索（投入负收益）。

**① 分母修正（已实现）**：`IntelRepository.coverage_report()` 给出**双口径**——
旧口径（分母=全部活跃文章，仅作对照）与新口径（分母=**趋势/事件类文章**，即"本来就该有事件的那类文章"）。
回填工具 dry-run 直接打印两行对照，验收**只看新口径**。

**③ 换真指标（已实现）**：`tools/qa_retrieval_acceptance.py` —— 使用侧验收，纯检索不调用 LLM：
- **命中率**：问题能取到证据（evidence 非空）
- **可回溯率**：每条证据都能解析回原文（`article:<id>` 可查、`edge:<key>` 能顺 `article_id` 回到原文）
- **词面接地率**：证据里真的出现问题的关键词（防答非所问）
- **图证据利用率**：多少问题用上了图谱事实（事件边/属性边）与有效期过滤
- 附带：平均证据条数、平均检索耗时（实测约 0.6 秒）、报错题数（取不到证据算"空"不算报错）
问题集可由 `--generate N` 按语料现况生成（事件问法/属性问法/时间窗问法三类），落盘后可手改。

**新验收清单（替换原来的"覆盖率 ≥ 60%"）**
| 维度 | 指标 | 口径 |
|---|---|---|
| 抽取·料 | 事件覆盖率 | **新口径**（分母=趋势/事件类文章），目标是逼近其天花板 |
| 抽取·料 | 属性/事件条数、带有效期属性条数、跨文章可聚合实体数 | 绝对值，报告出来 |
| 图谱 | 边覆盖率（事件边/事件行）、属性有效期可检索、邻域可用 | 100% / 已实测通过 |
| 使用 | 检索命中率、可回溯率、词面接地率、图证据利用率 | `qa_retrieval_acceptance.py` |
| 红线 | `other` 类不纳入抽取（避免污染图）；占位行比例如实报出 | 不隐瞒 |

**明确不做**：不为凑 60% 而放宽到 `other` 类（多花约 20 小时模型时间、且会污染图，上限也只有 54~57%）。

## 阶段 8.5：属性边（主系表/数值断言）+ 检索按边类型配套（✅ 已交付）

**为什么单独做这一层**：事件口径只收"有动作、有变化"的句子，像
「最近生产的模型是高精度的模型，2027 年发布的模型是低延迟模型」这类主系表陈述
**没有动作**——实测把这句话送进原 prompt，模型直接返回 `{"events":[]}`，整条丢失。
但它恰恰是可检索、可推理的事实，而且带**有效期**（"2027 年发布"= 从 2027 起成立）。
**建图不接线等于没做**，所以本阶段同时改了检索算法。

**本轮已做（2026-10-09）**
1. ✅ **一次调用同时抽事件与属性**（不额外增加 LLM 成本）：
   `build_event_prompt` 增加属性字段说明；`validate_extraction_output()` 返回
   `{"events":[...], "attributes":[...]}`（`validate_event_output` 保持向后兼容）。
   属性字段：subject / attribute / value / value_type(name|code|quantity|text) /
   **valid_from / valid_to / as_of** / evidence_quote。
   **有效期只认文中明写**（`_clean_date_text` 归一成 YYYY / YYYY-MM / YYYY-MM-DD，
   写反了自动交换，看不出就留空）——属性**允许未来有效期**，所以不做"未来日期"拦截。
2. ✅ **落库**：新表 `intel_article_attributes`（主体/属性/值/有效期/原文片段/content_hash）。
   0 条属性**不写占位行**（属性抽不到是常态，不该污染表）。
3. ✅ **建图**：`kg_edges` 新增 `relation_kind`(event|attribute|cooccurrence)、`attr_key`、
   `attr_value`、`value_type`、`valid_from`、`valid_to`、`as_of`、`evidence_quote`；
   `kg_nodes.node_type` 增加 `value`（属性值也建节点，便于反查"哪些主体是高精度"）。
   边身份：事件边 = (src, action, dst, article)｜属性边**额外带 attr_key**——否则同一主体
   在一篇文章里的"精度定位/延迟定位"会互相覆盖。
   旧结构自动重建（图是派生数据），重建时打印条数，不静默丢。
4. ✅ **检索配套（核心）**：`qa_retrieval.graph_evidence()` —— 独立图证据通道：
   · **按边类型加权**：`graph_intent(question)` 判意图——问"是什么/定位/现状"→ attribute 1.0 /
     event 0.55；问"发生了什么/最新动态"→ event 1.0 / attribute 0.55；分不清 → 1.0 / 0.8。
     最终分 = 100 × 类型权重 × 边置信度 + 来源文章权威度×0.1。
   · **有效期过滤**：属性边只在"查询时点落在 valid_from~valid_to 内（空=开区间）"时参与检索；
     事件边不受影响。
   · **包隔离**：`edges_for_nodes(pack_id=...)`，不得跨包取证据。
   · **可回溯且不挤掉全文**：图事实的 `article_id` **刻意留空**——留了会被上游按 article_id
     去重、把源文章的全文挤掉；可回溯性放在 `metadata.article_id / article_url / graph_edge_key`。
   · 名额受限：`QA_GRAPH_MAX_ITEMS`（默认 4）且不超过检索上限的 1/3，绝不挤光文章证据。

   证据契约同步扩展 `source_type` 枚举新增 `graph`。
5. ✅ **补存量**：`backfill_article_events.py --refresh-attributes` —— 对"抽过事件但还没有属性行"
   的文章重抽（同一次调用同时刷新事件与属性，幂等）。
6. ✅ CLI：`build_knowledge_graph.py --relation-kind event|attribute --as-of YYYY-MM-DD`，

**边界**：属性只抽文中明写的事实（禁止从常识补全）；有效期不确定就留空（开区间，宁可多留不误杀）；

## 阶段 9：规则引擎 + 多跳子查询分解

**目标**：从"关键词 + 语义打分"升级到"逻辑驱动的定向检索"。

**子任务**
1. `intel_business_rules`（条件 → 动作）表化，现有 `pack_attention_directions`/`fixed_topics`/`core_keywords` 作为 `source=pack_config` 迁移。
2. `qa_planner._CATEGORY_RULES` 补四类：`conditional_constraint` / `causal` / `temporal_relation` / `multi_hop`。
3. 子查询分解器 `qa_query_decompose.py`：输出带 `depends_on` 的有向无环子查询图。
4. 多跳执行：按 `depends_on` 顺序执行，上一跳结果作为下一跳的实体/过滤条件（LLM 只做兜底）。
5. `logic_validation` 阶段：因果检查、条件满足检查、缺失链接检测。

**边界**：多跳必须受 `qa_resilience` 预算约束；规则迁移需与行业包发布流程配合（已发布版本优先，改文件不生效）；不改变单跳问题的既有路径。

**测试方式**：规则命中单测；子查询图结构单测；端到端多跳问题（A 对 B 的影响 → 路径）与单跳对照；预算超限时的降级行为。

**验收标准**：四类问题能被正确分类；多跳问题产出的子查询图可执行且每跳有证据；预算超限时降级为单跳并明确告知用户。

   **只有"问题带时间窗 + 硬过滤开 + 窗口内候选 ≥ `QA_TIME_MIN_IN_WINDOW`"时才收窄候选集**，
   否则原样返回（窗口内不够就收窄，等于把阶梯扩窗的退路堵死）。
   开关 `QA_VECTOR_PREFILTER`（默认开，=0 与旧行为一致）；命中情况写进
   `stats.vector_prefilter`（`candidates / in_window`）可审计。
3. ✅ **多向量召回**（原文 + 简繁/英文别名）：`qa_retrieval._vector_variants()` 由
   `qa_query_normalize.expand_terms` 生成变体（上限 `QA_VECTOR_VARIANTS`，默认 3），
   每个变体各算一次语义分，**同一篇文章取最高分**（不是相加、也不是最后一路覆盖）；
   `QA_VECTOR_VARIANTS=1` 时只有原文一条 → 与旧实现逐条一致，便于做等价对照。
4. ✅ **硬约束命中直接置顶**：权重表新增 `hard_constraint_pin`（**默认 0 = 与旧行为一致**），
   `hard_pinned` 档置为 5000 → 法规号精确命中 / 数值命中直接置顶，并在 reasons 里写明
   "硬约束置顶（…）"（顺序可解释）。

**测试方式（已实现）**：`tests/test_qa_vector_conditional.py`（13 例）：
单变体=旧行为、多变体含别名扩展、变体数受环境控制、多路召回取最高分、
前置过滤五态（够用收窄 / 不够保持原样 / 开关关闭 / 无时间窗 / 硬过滤关闭）、

## 阶段 12：worker 吞吐与队列治理（**本轮已动手**）

**为什么单列**：分类/精炼/向量这些"入库后处理"的积压不是功能缺陷，而是**吞吐缺陷**——功能都对，但队列永远排不空，等价于这些能力没生效。

**A 机实测（10-06，只读体检）**
| 指标 | 数值 |
|---|---|
| core lane 总吞吐 | **53.4 个作业/小时**（14 小时完成 748 个） |
| classification 完成 | **0.8 个/小时**（14 小时 11 个） |
| classification 到达 | 稳态约 11 篇/小时；另有 10-06 07:00 一次性入队 **5145 个** |
| 当时积压 | 5314 排队，最老等待 **30.4 小时** |
| 按现速率排空 | **6773 小时**（约 9 个月） |

**根因（三条，按影响排序）**
1. **批次串行**：`IntelWorker.run_once` 一次性原子领取 `INTEL_WORKER_BATCH_SIZE=20` 条后**逐条串行**执行（原注释即 "processed sequentially"）。作业耗时几乎全在等 LLM/网络 → 整条 lane 被串行等待卡死。
2. **优先级形同虚设**：`INTEL_JOB_PRIORITY_AGING_SECONDS=30`（每等 30 秒 +1 优先级），任何等待超过约 1 分钟的作业都盖过任意优先级设置 → 实际退化成纯 FIFO；而 `classification` 是唯一的 `priority=10`（最低），长期排在所有维护类作业之后。实测 FIFO 头部全是 31 小时未尝试的 `trend_aggregate`(-45) / `topic_cluster`(-40) / `embed_articles`(-30)，`classification`（最老 30.5 小时）排在它们之后。
3. **容量黑洞**：`enrich` 反复失败（`VPN 返回空精炼内容`，55 个作业累计 220 次尝试）；`embed_articles` 对本地 embedding 端点 **100% 失败**（`input (527~1305 tokens) is too large to process; current batch size: 512`），失败批次还要拆单重试 —— 实测在跑的 7 个作业里有 **5 个是 32 小时前入队、反复重试的 `embed_articles`**，长作业把并发槽位占满。

**本轮已做**
- ✅ **批次并发**：抽出 `_process_claimed_job`，`run_once(concurrency=...)` 支持有界线程池（计数加锁、单条异常隔离），新增 `INTEL_WORKER_JOB_CONCURRENCY`（**默认 1 = 与历史行为一致**），先设 4 观察一轮，现已提到 **8**（A/B）。新增 `tests/test_worker_job_concurrency.py`（5 例，完全隔离，不触碰真实作业）。
- ✅ **embedding 输入上限**：实测 A 机的 bge-m3 是 llama.cpp 起的（`10.88.0.1:8082`，物理批大小 512），>512 token 输入一律 500 → `embed_articles` 送整篇正文 **100% 失败**、拆单重试仍全失败。现在客户端按 token 估算截断到 480（`INTEL_EMBEDDING_MAX_INPUT_TOKENS` 可调），并在服务端回"输入过长"时**缩小输入再试**（而不是原样重试）。实测同一端点：800/1500/3000 字符与 16 条批量全部成功落 1024 维向量。
  ⚠️ **服务端重启仍需人工**：`10.88.0.1:8082`（A 机用）与 `192.168.0.18:8082`（开发机用）两台都**没有可用 SSH 凭据**（实测 `Permission denied (publickey,password)`），我无法重启。要恢复完整语义（不截断），请在其中一台上用 `-ub 2048 -b 2048` 重启 llama.cpp 的 bge-m3（服务已声明 `n_ctx=8192`，bge-m3 支持 8192 token），然后把 `INTEL_EMBEDDING_MAX_INPUT_TOKENS` 调大或设 0。
- ✅ **enrich 失败语义**：以前「VPN 返回空精炼内容」一律可重试，55 个作业烧了 **220 次尝试**。新增 `_enrich_failure_is_permanent()`：VPN 判定无相关内容（`relevance=none`）、内容类型不是文章（list/aggregation/navigation/index）、原文短到无法提炼 → **永久失败不再重试**；模型抖动/超时仍可重试。`article_id 缺失`、`VPN 未被配置` 也改为不可重试。
- ✅ **优先级语义（三处一起改才有效）**：① aging 30 → **600 秒**（原来任何等待超 1 分钟的作业折算积分都盖过任意优先级，退化成纯 FIFO）；② 新增 `INTEL_JOB_PRIORITY_AGING_CAP=90` 给等待积分**设上限**（否则等得够久照样盖过一切：实测 28.8 小时未处理的 `trend_aggregate(-45)` 折算 +172，压过优先级 100 的分类）；③ 分类优先级 10 → **100**（`enqueue_job` 允许上限，实测 150 会被 `coerce_int(...,-100,100)` 截到 100）。现在维护类最高的 `candidate_dispatch/candidate_rescore(+5)` 折算后 95 < 分类 100 → **分类只要在排队就先被领取**，分类队列空时其它类型照常执行。
- ✅ **产品决策钉死**：零行业信号的文章**不得**进 AI 证据池 —— 新增 `tests/test_retrieval_evidence_policy.py`：闸门语义（空命中/低于阈值一律拒绝）+ 源码守卫（`_rows` 不得出现 `result_source` / `fallback_attribution` 特例）。

**并发生效后的实测（A 机，30 分钟窗口）**
| 指标 | 改造前 | 并发=4 | 并发=8 + 优先级修复 |
|---|---|---|---|
| core lane 总吞吐 | 53.4 个/小时 | **68.0 个/小时**（+27%） | 见下方观察轮 |
| classification 完成 | 0.8 个/小时 | **16.0 个/小时（20×）** | 见下方观察轮 |

**为什么并发不是线性收益**：整条 lane 吞吐 = 并发度 ÷ 队首作业平均耗时。队首是 `enrich`（31 小时前入队、带 LLM 精炼）与 `trend_aggregate` 这类数百秒的作业，所以 4 并发只换来约 2 倍多的实际吞吐；`classification` 本身很快（8 个在同一秒内完成）。**要真正排空积压，并发之外还必须清掉容量黑洞 + 修正优先级语义**，这三件本轮都做了。

## 全局纪律（每个阶段都适用）

1. **本地是唯一标准**：先在本机改 → 真跑测试 → 推 `origin/main` → 部署 A/B → 生产真实验收。
2. **禁止"读代码就算验证"**：每个验收点必须真跑（真库、真 HTTP、真浏览器点击、真 LLM）。
3. **每台机器都要确认"模型真的被调用了"**：不看接口通不通，看 `qa_stage_runs` 里
   `level1_draft` / `synthesis` 的耗时与 `qa_runs.degradation_json`——耗时百毫秒级 + degraded=1
   就说明没调到模型（B 机的事故就是这样被发现的）。私网端点必须进白名单。
4. **回归用前后对比**：本仓库 `tests/` 全量本身有大量既有失败（实测基线 `133 failed / 1046 passed`），
   一律以"改动前后同批用例的通过/失败数量与名单"为准。
5. **失败要留痕**：入库被闸门拒绝、归因/影响力降级、会话回退，都要打印带来源的日志，便于运营定位。
6. **可逆**：回填类工具必须先导出备份、支持 dry-run；软删除优先于物理删除。
7. **不加依赖、不推倒重构**：优先接线已有能力（事件抽取、实体归一、claim、冲突、证据分组都在库里）。
8. **代理值必须标注**：词元影响力等近似能力必须在返回体与 UI 上写明 method，不得冒充梯度归因。
